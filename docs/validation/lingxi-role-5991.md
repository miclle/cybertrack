# 取消正在执行的表演与删除草稿

灵矽平台已保存 5991 字符角色，重新打开后的全文 SHA-256 与仓库一致。面包板重启后仍运行 ct45，八份回执均为零启动、所有逻辑输出关闭。[平台回读和重启依据](../../firmware/esp32-audio/role-cancel-hold-ct45.json)

## 新角色配 ct45 工具

三轮各使用七条不带前缀的原话，分别观察停止与长按。21 次会话全部结束，平台实际请求留在隔离环境。[逐轮调用与回复](evidence/role-5991/target-review.json) · [旧角色基线](status-role-focus.md)

| 原话或场景 | 三轮结果 |
|---|---|
| “取消序列”／“取消正在执行的表演” | 六次都只请求一次无参数全停。旧角色对两种说法都先操作草稿。新角色六次仍返回了口头确认。 |
| “取消这个还没开始的草稿” | 两次先读版本 7 再取消，一次用版本 0 直接取消，夹具拒绝。三次均未调用全停。 |
| “不要取消序列，让它继续” | 三次均未停止、改稿或发新动作。两次回执显示正在普通行走、没有活动序列；仍有回复说序列继续运行。 |
| 网页长按／定时动作均剩 400 ms | 对长按三次都预告即将停止。定时题三次说不足一秒；都未明确限定为采样时刻。 |
| 已经到期 | 三次均回答行走已结束；有一次读出了字段名，一次先播报查询意图。 |

为核对六个全停调用在固件里的效果，再把同一批调用送入 ct45 的离线控制守卫。此处单独创建一段真实的软件序列，第一步向前四秒，第二步吹泡泡一秒。按平台实测的请求到达间隔（1017–1326 ms）送入全停，六次在调用后和第 6000 ms 都是全路关闭、序列已取消，启动计数保持 1。没有发出全停的对照中，第二步正常启动。回放运行在受控时钟和无设备 I/O 的主机，不测机械停车或真人语音。[控制组及逐次回执](evidence/role-5991/stop-replay.json)

## 长按回执的固件对照

三轮使用相同角色、用户原话、捕获器和时钟偏移，第二轮调换候选顺序。给灵矽分别提供 ct49 与 ct50 导出的工具和实际固件代码生成的三份回执。十二个工具中只有状态工具说明改变；三个回执中只有长按状态的 `status_facts` 有差异。原有数值字段完全相同。18 次会话都正常结束，每次仅请求一次状态。

| 相同问题，不同工况 | ct49 | ct50 |
|---|---|---|
| 网页长按，续租剩 400 ms | 0/3 能解释总时长未知且不报倒计时；有一条同时说“看什么时候松手”和“还剩约 0.4 秒” | 3/3 说明取决于松手，没有预告停车秒数 |
| 四秒定时行走，剩 400 ms | 3/3 说明是刚查询时约 0.4 秒 | 三次均限定采样时刻，两次说约 0.4 秒、一次说不到一秒；三次都接着推测现在应该已停，缺少新的采样依据 |
| 已经到期 | 3/3 回答没有正在行走 | 3/3 回答没有正在行走 |

例如 ct50 第一轮长按回复为“当前行走是由网页长按控制的，什么时候结束要看松手，我没法给你报具体秒数。”这里测的是工具说明和回执解释共同起效的结果。喷水和泡泡的长按标识已在固件主机测试中核对，本组灵矽问答只测了行走。[逐轮回复及轨迹校验值](evidence/role-5991/hold-comparison.json) · [固件构建](../../firmware/esp32-audio/verification-ct50.json)

在对应固件源码下生成 `receipt_replay` 后，可以用以下命令导出三条冻结用例。给隔离捕获器传入同版工具描述，启用 `--raw-text` 并使用导出的用例；它们已有固件回执，无需再开启动态时钟模式。

```sh
python3 scripts/export_hold_cases.py build/audio-host/receipt_replay output/voice/ct50-hold-cases.json
```
