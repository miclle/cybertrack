# 调速拒绝作为工具结果返回

2026-10-31，用同一角色、工具定义、Tingting 音色和“全速”原话，对照 JSON-RPC 错误与明确拒绝的工具结果。线上角色仍为 5991 字符。工具由无设备 I/O 的固件主机应答，输入走灵矽真实 Opus 识别。

## 三轮对照

空闲、设备语音链路离线和设备 Wi-Fi 离线各测三轮。每轮先测 RPC 错误，再测结构化结果；时间顺序是本实验的限制。18 次均正常结束，仅请求一次 100% 绝对调速，主机回读均为零启动、全路关闭。

| 返回方式 | 空闲 | 语音链路离线 | Wi-Fi 离线 |
|---|---|---|---|
| JSON-RPC 错误 | 0/3 明确原因，首轮猜测多种可能 | 0/3 明确原因 | 0/3 明确原因 |
| `result=rejected` 的工具结果 | 3/3 说明未移动 | 3/3 说明语音控制链路离线 | 3/3 说明设备 Wi-Fi 离线 |

结构化组中的原始错误文本与 RPC 组来自相同主机控制代码，结果额外提供操作名、`rejection_reason` 和 `physical_feedback=false`，此次同时改变了返回通道和结构，不能据此将改善全部归因于其中单个字段。九条回复均未建议试动或自动重试。

## ct57 实际接入

ct57 对绝对和相对调速的票据拒绝，使用共享 C++ 序列化器返回 MCP 工具结果，内部明确为 `rejected`。未取得票据即返回，操作回调不会进入调度队列。其他工具的票据拒绝继续使用现有 RPC 错误。序列化失败时回退 RPC 错误。角色和工具参数均沿用当前定义。

另用实际 ct57 主机程序运行四次独立会话，去掉实验转换开关。两组错误文本和内部拒绝语义按实际收到的调用重新计算核对。

| 主机初态 | 灵矽回复及主机结果 | ct57 逐包播放策略 |
|---|---|---|
| 空闲 | “当前没有在移动，速度调不了。”零启动、全路关闭 | 44 个提示包全部保留 |
| 语音链路离线 | “语音控制链路离线，这次没调成速度。”零启动、全路关闭 | 56 个提示包全部保留 |
| Wi-Fi 离线 | “设备Wi-Fi离线，这次没法调速。”零启动、全路关闭 | 40 个提示包全部保留 |
| 70% 向前定时移动 | 正确设为 100%，启动计数仍为 1，方向和原截止保持 | 28 个成功确认包全部抑制 |

这四次核对了实际主机回执路径；板上最近记录仍为 ct45。相对调速的序列化与拒绝保护由主机测试覆盖，本轮平台原话只测试绝对调速。真人拾音、现场断网和扬声器听感继续等待现场验收。

## 复核

[逐条记录](evidence/admission-envelope/review.json)包含全部 22 次的回复、调用、最终状态和包数。原始压缩轨迹同目录保存，每份均附未压缩 JSON 的摘要。主机程序按每条记录的调用时间重放，匹配全部回执和最终状态；音频内容已丢弃。

[对照采集入口](lingxi-capture.md#对照-rpc-错误与拒绝结果)保留实验方法。运行实际 ct57 时先用其源码执行 `run_mcp_tests.py`，随后运行普通 `--speed-host` 采集，不传 `--admission-result-fixture`。固件构建身份与本地检查见 [ct57 软件记录](../../firmware/esp32-audio/verification-ct57.json)。
