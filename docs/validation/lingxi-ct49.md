# 剩余时间在什么时候有效

用户听到“还有 2.7 秒就停了”时，机器人可能已经停下。ct49 的状态工具要求把剩余量明确归于采样瞬间，询问播报结束后的运动状态时说明无法保证。固件仍按原截止时间关断。

三轮对照各使用同一组四条原话，ct48 和 ct49 各 12 次，交替安排先后顺序。角色、捕获程序、主机回执二进制及用例哈希一致。两份导出的 12 个工具中，只有 `self.tank.get_status` 的说明不同。平台的每次只读查询都按 RPC 实际到达时间读取固件主机状态，动作初始期限为 4000 ms 或 400 ms。24 次会话全部完成，每次只调用一次查询，均未请求动作。[用例](status-timing-cases.json) · [联调方法](lingxi-capture.md)

| 原话的要求 | ct48 | ct49 |
|---|---|---|
| L001 只问方向，不附带倒计时 | 0/3，均附带剩余秒数 | 0/3，仍均附带剩余秒数 |
| L002 询问还要多久，按查询时刻报剩余量 | 0/3 明确限定采样时刻 | 3/3 明确说“刚才查询时”，秒数与回执按十分之一秒取近似值一致 |
| L003 询问听完回复时是否一定还在走 | 0/3 明确表示不能保证 | 3/3 明确表示查询时在走、听完时可能已停 |
| L004 查询到达前已过期，不猜测停机原因 | 3/3 说明行走已结束 | 3/3 说明行走已结束 |

例如第三轮 ct49 的时长问题，查询在输入发出后 1249 ms 到达。受控时钟下原有 4000 ms 还剩 2751 ms，回复说“刚才查询时还在往前走，剩余约 2.8 秒”。方向题仍出现用户未问的数字，第一轮还有一段查询意图自述。该对照只覆盖这组文本，现场调度、扬声器播报与机械停止仍待测。[逐例回复及采样时刻](evidence/status-timing/review.json) · [原始轨迹](evidence/status-timing/) · [固件构建记录](../../firmware/esp32-audio/verification-ct49.json)
