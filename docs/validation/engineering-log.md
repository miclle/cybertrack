# 工程修改与 AI 使用记录

对应 I10。目标是积累 5 次真实工程修改的时间、返工和验证证据，回答 AI 如何参与设计与实现、哪些环节减少重复劳动、哪些环节仍需要人工判断。提交数量、代码行数和工具调用数都不能单独证明效率提升。

[engineering_log.py](../../scripts/engineering_log.py)提供本地开始、结束和汇总入口。开始／结束命令需要完整 CyberTrack Git checkout；解压参考材料包不等于取得完整仓库。记录默认写入忽略目录 `output/engineering/`，不发送到外部服务、不调用模型，也不写入 Git 配置。当前没有已采集的完整实际样本；单元测试的临时仓库与合成时间不会进入实际记录。

## 开始一项真实修改

在开始实施时运行，不能替之前的工作倒填开始时间：

```sh
python3 scripts/engineering_log.py start <本次唯一编号> \
  --summary '<问题、预期结果与 AI 参与的具体环节>'
```

开始记录自动包含 UTC 时刻、当前提交和工作区是否有修改。若实施已经开始，应在说明中写明“从验证／修复阶段开始记录，前期时间未采集”；后续间隔只代表该记录窗口，不能当作完整任务耗时。

按实际情况及时记录人工工作时间、模型等待时间、修正轮数、失败检查次数和回归缺陷。未计时的字段保持未知；没有观察到不等于零。用户无交互、模型自动运行的时段不能凭想象补成人工工作时间；总墙钟时间也不能直接当作模型等待。

## 提交后绑定证据

完成实际修改、必要检查与范围明确的提交后，使用明确提交哈希结束记录：

```sh
python3 scripts/engineering_log.py finish <本次唯一编号> \
  --commit <本次提交哈希> \
  --evidence output/improvements/checks/<实际检查目录>/report.json
```

`--evidence` 可重复，必须是仓库内已有文件。工具记录路径、字节数和 SHA-256，不复制证据内容。既有检查报告、编译日志、原生 CAD 回读或浏览器验证产物可作为证据；必须注明其实际覆盖范围。工具只证明文件身份，不推断检查通过或实物合格。

有真实记录时再添加以下可选参数；未填写会保存为 `null`：

| 参数 | 含义 |
|---|---|
| `--human-minutes` | 实际人工工作分钟数 |
| `--model-wait-minutes` | 实际记录的模型等待分钟数；不包含未区分的闲置时间 |
| `--revision-rounds` | 依据失败或反馈重新修正的轮数，非负整数 |
| `--failed-checks` | 本次失败的检查次数，非负整数，后来通过不抹去先前失败 |
| `--regressions-found` | 已发现的回归缺陷数量，非负整数；未检查填未知 |

结束提交必须是记录开始后的新提交，且开始提交是它的祖先；不能把开始前的同一提交重新当作交付。一项提交只记一份修改记录，不用多个编号凑齐 5 次。开始／结束文件均不覆盖，结束记录绑定开始文件哈希；系统时钟倒退时拒绝计算间隔。

## 汇总与解释

```sh
python3 scripts/engineering_log.py report \
  > output/engineering-report.json
```

汇总会核对开始记录是否被改动、提交是否存在且继承基线、证据文件是否仍存在且哈希一致，并逐项列出未知数据。缺结束记录、缺人工／等待／返工数据或证据变化，均不计入 `complete_records`。不能用缺值填零来完成指标。

记录齐全仍不等于效率提升。`efficiency_improvement` 始终为 `not_established`：要估计提升比例，另需相同复杂度、相同质量门槛的可比基线，还需解释熟悉度、任务差异、并行和返工的影响。当前工具不自动生成改善百分比。

在比赛材料中，可以据实际记录展示“问题 → AI 辅助方式 → 人工判断 → 验证 → 提交”的过程，例如 SolidCue 的带版本评论、原生属性修改和恢复，或语音工具契约与固定集回归。案例具体做了什么、为何返工、验证了什么，比无依据的效率百分比更有说服力。未经观测的字段和待验环节应保持明确。
