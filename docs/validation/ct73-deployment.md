## 接下来的现场顺序

1. **恢复受测功率并核对场地。** 仅恢复行走／喷水／泡泡，点火支路保持断开。确认 BOOT 与独立断功率可触及，记录地面／架空状态、负载和供电版本；现场就绪前不发动作。
2. **短动作与停止。** 先以明确速度和短时长逐路检查方向、实际效果与到期停止，再测试松手、网页全停、本机 BOOT。异常立即全停并保留失败，不自动重试或补做。
3. **恢复与来源。** 分开验证网页断线、设备 Wi-Fi 断开及语音连接关闭；恢复后不发新启动，观察旧动作与后续步骤是否恢复。网页静默失联须等设备检测租期，不能把手机断线时刻当作设备已经关断。
4. **真人语音与剧场。** 先检查普通动作、停止、否定和状态问句，再验证草稿不启动、修改预览、网页明确确认、执行和中途停止。分别记录工具接受、实际动作和听到的回复；不测试点火／狂暴模式。
5. **完整覆盖与负载。** 首轮排查之后按[17 案例矩阵](stop-trials.md)每条件至少五次正式采集，再做组合负载／温升／续航和维护。缺仪器时只记录可观察现象，输出关断时间、机械停止时间、位移与误差未知保持 null，不填 0。

此前还有一次[未启动的连接超时](evidence/ct73-first-motion/not-started-connection.json)：pair 请求超时，尚未发送动作；附加串口监听出现初始化日志，之后 HTTP 恢复。两轮启动时间轴表明期间发生过重启，但原因未确定。后续动作只用 HTTP，不重新打开串口，观测期间启动身份保持；不能把此前重启归因为电源或固件。

失败后的[状态回读](evidence/ct73-first-motion/post-failure-state.json)为全停、逻辑输出全关、无输出故障报告、启动计数仍为 1，网页偏好已恢复 100%。[输出驱动对比](evidence/ct73-first-motion/output-source-comparison.json)确认 ct45／ct73 的 `action_outputs.h` 摘要一致；控制会话和工具适配不同，因此该相同性不能排除其他软件路径或硬件问题。

随后用户补充“电机没有问题，我用手机打开网页测试是正常的”。该正常反馈与失败的 60%／500 ms 定时请求分列；用户随后确认速度为 100%、“时间很短也能转动”；准确按住时长未测，不推定电机或供电故障，也不据此把所有电气验收标为通过。

保持前进请求 500 ms 不变，改为 100% PWM 做对照。第一次 100% 请求有完整回读，但用户说“没注意”，只记[未观察](evidence/ct73-first-motion/first-motion-100pct-03.json)，不计物理通过或失败。用户明确要求再执行后，[另一次 100% 请求](evidence/ct73-first-motion/first-motion-100pct-04.json)被接受，用户确认“两侧都转动，随后停止”。这只证明该次架空条件下的基本功能；不证明精确运行时间、停车性能或低占空比启动阈值。

源码显示手机方向键使用 `drive_start`／`drive_renew`／`drive_stop` 长按租约，而本次使用 `move(duration_ms=500)` 定时路径，两者最终进入相同底层输出适配。后续先核对手机参数，再在相同架空条件下选择只改变一个因素的受控对照；不强制先测待机电压，也不自动改为更高占空比或更长时长。没有调整升压、更换接线或追加固件写入。本例不属于 17 类正式停止矩阵，完整物理覆盖仍未增加。
